Разработай PoE Flip Overlay: лёгкое кроссплатформенное desktop-приложение для поиска выгодных валютных флипов и цепочек детерминированных обменов. ## 1. Окончательный технический стек

Первый релиз: Windows 11 x64 + PoE1. Совместимость с Windows 10 22H2 проверять отдельно с учётом поддержки ОС/runtime. Будущие расширения: Linux и PoE2 — независимые этапы, не обязательные для MVP. Общее ядро и UI должны изначально собираться для Linux без WPF/WinForms/Win32-зависимостей. Полноценный Linux-оверлей требует отдельной проверки оконной среды; не обещать одинаковое поведение на всех compositor. Игра — Borderless Windowed или обычное окно; Exclusive Fullscreen вне MVP.

Использовать:
- C# / .NET 10 LTS. Общее ядро, инфраструктура и UI — net10.0; Windows-specific interop изолировать в отдельной сборке/адаптере. SDK закрепить в global.json, пакеты — в lock-файлах. Никаких Windows-only типов в публичных контрактах общих модулей.
- Avalonia UI/XAML (.axaml), MVVM через CommunityToolkit.Mvvm, compiled bindings. Использовать поддерживаемую stable-версию Avalonia с бесплатными open-source контролами, совместимую с .NET 10; до реализации закрепить точную patch-версию и лицензии в docs/STACK.md. Не использовать nightly/previews и коммерческие контролы. Стандартные стили с лёгкой собственной темой, без второго UI-фреймворка.
- UI baseline: Avalonia 12.1 или более новая поддерживаемая stable-ветка; актуальную совместимую patch-версию зафиксировать до кодирования. Table: встроенный TableView из Avalonia.Controls (доступен с 12.1). List: ListBox с VirtualizingStackPanel. Не брать deprecated DataGrid или коммерческий TreeDataGrid. Единая ResultProjection для числовой сортировки/фильтров и incremental updates обоих представлений; без WPF ICollectionView/ListView. Ограниченная высота контейнеров и проверка реальной виртуализации обязательны. Не создавать визуальные элементы для всех записей заранее.
- Платформенные IOverlayWindowService и IHotkeyService с capability flags. Windows: Win32 LibraryImport только для своего окна и RegisterHotKey, обработка сообщений через поддерживаемую интеграцию Avalonia; не использовать WPF HwndSource. Linux: отдельный будущий адаптер; не эмулировать Win32 поверх общих модулей. Никаких hooks игрового процесса или глобальных low-level перехватчиков.
- HttpClient с переиспользуемыми соединениями, System.Text.Json, async/await, CancellationToken; TimeProvider для проверяемого времени и Stopwatch для замеров. Без браузерного движка и фонового веб-сервера.
- Microsoft.Data.Sqlite, параметризованные SQL-запросы и транзакции; без Entity Framework. Один последовательный writer, ограниченные очереди. Для portable на съёмных носителях не предполагать безопасность WAL: проверить файловую систему и предусмотреть rollback journal.
- JSON: настройки, каталог валют, рецепты, профили источников. Theme — Avalonia ResourceDictionary/Styles в .axaml. CSV — экспорт по запросу пользователя.
- xUnit, Microsoft.NET.Test.Sdk, встроенные .NET analyzers и dotnet format. Тесты времени — с подставным TimeProvider; HTTP — с подставным HttpMessageHandler. Не требовать живой сети для unit-тестов.
- Поставка: dotnet publish, Release, win-x64, self-contained, folder deployment. PublishSingleFile=false, PublishTrimmed=false, PublishAot=false. ReadyToRun включать только после A/B-замера старта и размера, не обещать пользу заранее.
- Inno Setup: per-user установщик. Portable ZIP из той же publish-папки. CI — GitHub Actions на Windows и Linux (общая сборка/тесты, Linux UI smoke без заявления о готовности игрового оверлея); сборка и тестирование не означают разрешения на публикацию.

Python, PySide6, PyInstaller, Electron, Chromium, WebView2, Node.js, Rust/Tauri и C++/Qt в runtime этого проекта НЕ использовать. Выбор C#/.NET + Avalonia окончательный для этой постановки: одна кодовая база UI/ядра для Windows и будущего Linux без браузерного движка. WPF/WinForms в UI запрещены. Это инженерный компромисс по всем требованиям, не доказательство абсолютного превосходства над Qt/Python или Electron по скорости и RAM. Сравнения без замеров не выдавать за факты. Производительность подтверждать spike и профилированием; при непрохождении gate сообщить результаты и запросить решение, не менять стек молча.

- Недоступность двух источников не является блокером сама по себе: один разрешённый источник с необходимыми свойствами лучше двух неподходящих. Блокер — отсутствие необходимых свежих данных.
- Частое скачивание часовой истории не превращает её в live-цены. HTTP 200 и время получения не подтверждают актуальность рынка.

### poe.ninja Economy — подтверждённый разрешённый источник аналитики

Добавить PoeNinjaEconomyProvider по первичной документации https://poe.ninja/docs/api. Документированные economy endpoints разрешены для стороннего использования; builds/profiles и прочие внутренние endpoints не использовать. API без SLA, контракт может измениться. Соблюдать ETag/Cache-Control, descriptive User-Agent с контактом, небольшой concurrency; не обходить cache. Автор рекомендует backend-прокси для кэширования; самостоятельный backend не добавлять в MVP без согласования, при массовом распространении отдельно согласовать схему/нагрузку с владельцем.

Проверенные запросы для PoE1:
- GET https://poe.ninja/poe1/api/economy/leagues
- GET https://poe.ninja/poe1/api/economy/exchange/current/overview?league={encodedLeagueId}&type=Currency
- При отдельной необходимости stash-based данных: /poe1/api/economy/stash/current/currency/overview?league={encodedLeagueId}&type=Currency. Не смешивать с exchange-данными.

На момент проверки реальный exchange-ответ содержит core/lines/items; поля строки primaryValue, volumePrimaryValue, maxVolumeCurrency, maxVolumeRate, sparkline. Это агрегатные оценки, НЕ текущие встречные заявки. Не выводить bid/ask, доступный stock и время наблюдения из этих полей. В проверенном response нет отдельного исходного timestamp; fetchedAt не исправляет этот пробел. Источник можно использовать для каталога, ориентиров, трендов и предварительного отбора кандидатов, но не выдавать их за подтверждённые исполнимые флипы.

Документация указывает примерно 5-минутный HTTP-cache с ETag и обновление исходных PoE1-overviews примерно раз в 15 минут (PoE2 — примерно раз в час). Это ориентиры провайдера, а не точные гарантии. Интервал выбирать по cache headers и исходному cadence; кнопка Refresh не делает агрегат новее. Без нового timestamp показывать Age unknown и expected cadence, а не Live. Этот провайдер снимает вопрос доступности агрегатной аналитики, но сам по себе НЕ снимает gate live-котировок NPC-биржи ниже.

### Остальные провайдеры и условия использования

PoeWatchProvider: документированный OpenAPI https://poe.watch/docs.yaml, сервер https://api.poe.watch. Для PoE1 использовать /leagues и /exchange/ratios?league={encodedLeagueId}&game=poe1 согласно актуальной схеме. Реальные ответы подтверждены: цены chaos/divine, lastTradeAt/timestamp, объёмы/история, lowConfidence; могут присутствовать сведения об окне и методе агрегации. Проверить семантику каждого времени и метода, не путать окно выборки с текущей котировкой. Не обещать SLA/частоту, которых нет в документации; получить условия лимитов/распространения перед массовым релизом. Это агрегатная аналитика, не live-orderbook.

GggExchangeHistoryProvider: официальный почасовой feed для проверки объёмов, диапазонов и истории. Публичный доступ не требует cookies; endpoint реализовать строго по документации. Показатели stock за исторический период не превращаются в текущую доступную глубину. Одинаковый первичный GGG-feed у разных агрегаторов не считать независимым подтверждением.

WealthyExileProvider — только кандидат: интерфейс/контракт без сетевой реализации и пометка Not configured. Получить публичную first-party API-документацию или письменное разрешение владельца, условия доступа/перераспространения, семантику цен и период обновления. До этого не обращаться к private endpoints/Next.js actions, не извлекать cookies и не скрейпить HTML. Сравнение цен лиги со Standard не является немедленно исполнимым same-league flip. Не добавлять фиктивный Wealthy-адаптер, возвращающий чужие или синтетические цены; заглушка должна явно сообщать Unsupported.

PoE Wiki: для каталога/рецептов/NPC-условий использовать документированный MediaWiki/Cargo API и локальный проверенный snapshot с атрибуцией. Лицензия лицензируемого материала CC BY-NC-SA 3.0, права GGG отдельно; до распространения определить совместимые условия для набора данных, не распространять лицензию wiki на весь код автоматически и не считать коммерческое использование разрешённым. Нормализовать только проверенные поля; null, неполное покрытие и условия NPC не игнорировать. Gold costs — справочная community-таблица с пробелами; округления и актуальность проверять вручную. Не загружать wiki при каждом refresh цен.

RePoE — необязательный источник metadata/stack sizes после проверки условий: MIT кода не лицензирует GGG-generated data. Не извлекать игровые файлы собственным приложением и не считать RePoE готовой базой gold fees.

PoE2 Scout — будущий PoE2-провайдер по опубликованной API-документации https://api.poe2scout.com/swagger. Сейчас только архитектурная точка расширения, не PoE1-интеграция и не обещание live-данных. На этапе PoE2 перепроверить schema, условия, timestamps, cadence, User-Agent/contact и реальные права на использование.

TFT/PoEHub, PoExplorer, Antiquary и любые другие публичные UI/JSON не подключать автоматически: наличие URL не является лицензией. Условия, происхождение и задержку подтверждать отдельно.

### Получение непосредственно из игры и trade-сайта

Документированный внешний API GGG — разрешённый путь при выполнении политики; почасовая Currency Exchange history не заменяет текущие заявки. На trade-сайте пользователь может вручную искать и сверять цены; приложение может открывать страницу по клику, но это другой рынок, не внутриигровая биржа.
Автоматический scraping HTML и недокументированные web-trade endpoints НЕ считать разрешёнными только потому, что их используют популярные инструменты. Не реализовывать без прямого подтверждения GGG для конкретного метода. Соблюдение rate limit необходимо, но само по себе не разрешает метод доступа.

В игре: ручной просмотр/ввод наблюдения пользователем допустим как ручная функция без автоматизации; clipboard — только по явной команде и с ручным Ctrl+C, если необходимые сведения вообще есть в копируемом тексте. Не утверждать, что Ctrl+C экспортирует стакан Currency Exchange. Чтение памяти, перехват трафика, инъекции и синтетический ввод исключены. OCR видимой информации без ввода нельзя автоматически объявлять ни однозначно разрешённым, ни равным memory reading: опубликованной гарантии для такого сборщика не найдено; в этом проекте OCR запрещён до отдельного согласования с пользователем и письменного уточнения GGG. Для запроса в support@grindinggear.com описать конкретный сборщик: только видимая пользователю биржа, частота/ручной запуск, скриншоты/OCR, отсутствие ввода и прямого взаимодействия с клиентом. Не отправлять письмо без отдельного разрешения.

### Расширение ручного подтверждения: OCR не включать молча

Предусмотреть IManualObservationSource и модель подтверждаемого наблюдения: game/league, пара и направление, количество, курс, золото, observedAt, provenance, confirmedByUser. Ручной ввод может работать без отдельного OCR-пакета. Будущий OCR — opt-in расширение за отдельными gates: явное согласие пользователя и уточнение допустимости конкретного сценария у GGG. До этого OCR-код, capture-loop и native OCR runtime не поставлять в MVP.
Только после выполнения обоих условий: импорт отдельного скриншота/явный пользовательский захват видимой области, локальное распознавание, просмотр и исправление всех значимых чисел перед подтверждением. Время старого скриншота не подменять временем импорта; неизвестное время = Unknown. Не нажимать кнопки в игре, не перебирать пары, не скроллить, не захватывать экран по таймеру и не распознавать невидимые данные. Две ноги маршрута требуют двух наблюдений, одно изображение не подтверждает весь маршрут. OCR-движок выбирать отдельным spike по поддержке Windows/Linux, лицензии, ошибкам распознавания чисел и ресурсам; не тянуть его в основной runtime заранее. Само существование OCR в Awakened или Path of Stonks не является разрешением GGG.

GGG публично не гарантирует допустимость сторонних программ навсегда. Корректная формулировка — минимизация риска соблюдением политики, не «без угрозы бана».

### Режимы результата и gate актуальности

Два раздельных набора, доступных в Table и List:
- Candidates: предварительные комбинации по агрегатам с Estimated profit, source quality/cadence и явной пометкой Verify in game. Они не смешиваются с текущими подтверждёнными наблюдениями и не называются Live. Если исходное время отсутствует — Age unknown; указать Fetched отдельно.
- Observed opportunities: рассчитанные по достаточно свежим направленным котировкам с источником/временем каждой ноги. Ручные наблюдения обозначать Manual, не Live API; их валидность также ограничена, повторная сделка не гарантируется. Нет подходящих данных — пустой набор с объяснением.

Оба режима — часть архитектуры, но выпуск только Candidates/manual вместо первоначально запрошенного автоматического live-сканера требует явной приёмки пользователем после spike. Не превращать потенциальный аналитический MVP в неразрешённый сборщик ради заполненной таблицы.

### Gate доступности live-данных
До построения production UI выясни: существует ли разрешённый источник текущих котировок ИМЕННО NPC Currency Exchange для PoE1, с временем наблюдения, направлениями обмена и подтверждёнными ограничениями.
Для стороннего провайдера изучи условия использования, происхождение, задержку и частоту обновления. Не называй его live только по маркетингу.

Результат spike: реальный обезличенный ответ и таблица «источник / рынок / доступ / лицензия или разрешение / время исходных данных / период публикации / bid-ask / depth / gold fee / лимиты».
Если разрешённого live-источника нет, остановись перед реализацией live-сканера и явно сообщи:
«Доступна только история; автоматическое ранжирование по актуальным котировкам NPC-биржи пока не подтверждено».
Предложи на выбор исторический аналитический режим с явной маркировкой или ручной ввод наблюдений. Не подменяй ими запрошенный live-продукт без согласия. Офлайн unit-тесты ядра можно писать до снятия блокера.

## 3. Безопасность: только внешняя аналитика

Запрещены:
- чтение/запись памяти игры, внедрение DLL, graphics hooks, драйверы, сетевой перехват;
- любые автоклики и синтетический ввод, даже «одна кнопка — одно действие»; автоматические покупки, продажи, отмены, NPC-обмены, whisper, приглашения;
- глобальные low-level keyboard/mouse hooks, фоновое наблюдение за вводом, сканирование экрана и OCR как источник автоматизации;
- внутренние недокументированные endpoints и обход защит, нарушение rate limits;
- скрытый автозапуск, телеметрия, сервисы и фоновые помощники.

Разрешено: собственное окно, RegisterHotKey для команд приложения, разрешённые HTTP-запросы, локальные данные; открытие страницы по явному клику пользователя. Чтение clipboard только по явной команде и только если эту функцию согласовали; пользователь сам нажимает Ctrl+C в игре. Не генерировать Ctrl+C и не отслеживать clipboard постоянно.
Price-check редких предметов и аналог Awakened целиком НЕ входят в MVP: референсы относятся к UX, не к расширению функциональности.

Проверка: ревью исходников и зависимостей, проверка запрещённых вызовов только в production-коде (не в документации и не в самом списке запретов), контроль отсутствия синтетического ввода. Статический поиск — дополнительный барьер, не доказательство отсутствия бан-риска. Не писать «100% ban-safe». Сомнительная функция отключается до подтверждения допустимости.

## 4. Актуальность: два независимых времени

Quote содержит:
game, realm, leagueId, marketKind, item pair/direction, sourceId,
observedAt или sourcePeriodStart/sourcePeriodEnd, fetchedAt,
sourceCadence, quality, bid/ask при наличии, depth при наличии, единицы и происхождение.

Разделить:
- Data age: возраст исходного наблюдения или конец периода агрегации;
- Fetched: когда приложение получило ответ;
- Market: NPC exchange / player trade / historical aggregate;
- Quality: LiveQuote / DelayedQuote / HistoricalAggregate / Manual / Unknown.

Не обновлять observedAt при повторном получении того же snapshot, 304, чтении из SQLite или нажатии Refresh. При отсутствии исходного времени — Age unknown; такие цены не участвуют в режиме актуальных возможностей. Возраст маршрута — возраст самой старой ноги. Нельзя смешивать рынки без явного маршрута перехода и реальных дополнительных действий.

В автоматический текущий рейтинг допускаются только разрешённые LiveQuote/DelayedQuote с допустимой исходной задержкой, известными направлениями и валидностью всех ног. Manual observation — отдельная явно отмеченная группа с пользовательским подтверждением и ограниченным сроком. Исторические данные могут участвовать в Candidates/Historical, но никогда не обозначаются доступной сейчас прибылью. Для Expected/Estimated расчётов модели цены не подставляются в поля исполнимых bid/ask.

## 5. Обновление данных и комбинаций

Не назначать «оптимальные 5–10 минут» без исследования. 5 минут — лишь начальная настройка для источника, у которого документально подтверждены достаточно частые обновления. Итоговый период и максимальный возраст определить по реальной периодичности публикации, rate limits, стоимости загрузки и изменчивости данных; записать обоснование и замеры. Не вводить псевдоточную формулу «полураспада» без статистической проверки.

Для почасового исторического API: обновляться после следующей публикации с ограниченным backoff; на конце потока ждать следующую часовую границу. Не опрашивать его каждую минуту.

- Асинхронный планировщик с отменой, один refresh-flight на источник, одинаковые запросы объединяются; параллелизм по умолчанию не больше двух сетевых запросов и одного расчётного задания.
- Учёт документированных лимитов, rate-limit headers и Retry-After; bounded exponential backoff с jitter на временные сбои. 401/403 — остановка и понятный статус, а не бесконечные retries.
- Refresh now и настраиваемый хоткей: обновление цен и последующий пересчёт маршрутов. Не обходить лимиты и не обещать новые данные, если источник их ещё не опубликовал. Показывать «No newer source data» или «Next source update …».
- Ручной refresh не запускает параллельный второй цикл. Минимальная локальная защита от повторов — 15 секунд, ограничения провайдера могут увеличить ожидание.
- Пересчитывать только затронутые маршруты при изменении значимых значений. Перерисовывать только изменённые строки.
- При скрытой панели по умолчанию продолжать разрешённое получение данных по расписанию; отключить UI-таймеры и рендеринг. Отдельная настройка Pause background refresh. Минимизация не должна незаметно отключать основную функцию актуальности.
- На истечении срока валидности строки немедленно исключаются из текущего рейтинга, даже без очередного HTTP-ответа. На экране — статус и реальное время последнего наблюдения, а не старые числа без предупреждения.
- Никакой анимации постоянного сканирования и polling-loop с коротким sleep.

## 6. Расчёт возможностей, золото и рецепты

Поддержать:
1. Купля/продажа валют при подтверждённом исполнимом spread.
2. Закупка валюты -> детерминированный обмен у вендора -> продажа результата.
3. Фиксированная покупка у NPC и продажа на подтверждённом рынке.
4. Ограниченные цепочки до четырёх шагов. Не строить бесконечные циклы и не перебирать все пути при каждом обновлении.

Каталог рецептов — версионируемые JSON-данные: inputs, outputs, количества, направление, NPC/акт/условия доступа, patch, source, checkedAt. Верифицировать каждую запись по актуальным данным и при возможности вручную в игре. Не переносить ошибочные рецепты из прошлых редакций ТЗ. «Chance -> Scouring» — кандидат для проверки, не заранее заданное отношение; обратимость рецепта не подразумевается. Случайный крафт, EV роллов и спекуляция ростом цены вне MVP.

Использовать decimal для цен и целочисленные количества; при дробных коэффициентах хранить точные отношения и учитывать округления/минимальные партии. Для заданного бюджета рассчитывать фактический размер партии, остатки, расход по каждой ступени глубины, если она доступна. Исторический объём торгов не считать доступным stock.

Профит = выручка от продажи партии − все затраты партии и подтверждённые торговые расходы в согласованной единице. Считать последовательность фактических операций, не суммировать произвольные средние цены в chaos. Конверсия в chaos — отдельная подтверждённая котировка с собственной актуальностью; если её нет, оставить исходную расчётную валюту.

Золото:
- отдельно по каждой постановке ордера на покупку И на продажу; учитывать золото за получаемую валюту на соответствующем шаге, если это подтверждает актуальная механика;
- таблица стоимости или формула с patch/source/checkedAt и ручной калибровкой по UI, не выдуманная константа;
- если точная формула не подтверждена — Gold estimated либо Unknown, диапазон и допущения. Unknown не равно нулю;
- корректная обработка частичного исполнения и отмены согласно проверенным правилам; не предполагать возврат золота;
- бюджет золота/капитала задаёт пользователь, баланс персонажа автоматически не считывается.

Обязательные метрики: Net profit/batch, ROI, Gold/batch, Profit per 1,000 gold, Capital required. При нулевом подтверждённом gold показывать No gold required, не Infinity; при неизвестном — Unknown. Неизвестные значения в сортировках всегда в конце, в обоих направлениях.
Profit/hour — только необязательная оценка при заданном пользователем времени выполнения и явных допущениях, не дефолт и не «измеренная ликвидность». Confidence не изобретать в виде необоснованного процента: показывать конкретные причины качества/риска.

Дедупликация маршрутов не должна убирать разные экономически значимые точки входа; соблюдать ограничения глубины без двойного использования одного и того же stock. Результаты — возможности по наблюдаемым котировкам, не гарантия исполнения. Перед сделкой пользователь проверяет рынок вручную.

## 7. Лиги и будущая PoE2

PoE1 — единственная реализуемая игра первого этапа. Общие интерфейсы IGameProfile, IPriceProvider, IRecipeCatalog, IGoldCostModel не должны знать конкретную игру. GameProfile определяет каталог, league discovery, reference currencies, правила округления/размеров стаков, доступные источники, рецепты и применимую модель gold. PoE2 получит собственный профиль, без копирования fee/rules PoE1 и без изменения общих формул.
В ключах данных использовать game + realm + leagueId + patch/catalogVersion + marketKind + source + instrument/direction; миграции SQLite версионируются. Строковые имена предметов — display values, не стабильные ID. ID из разных провайдеров сопоставлять через контролируемый mapping, не fuzzy matching торговых расчётов.
Не писать сейчас PoE2-сетевую интеграцию и не показывать неработающий переключатель игры. Отдельный PoE2 gate: собственные текущие источники, gold-механика, рецепты, лиги и реальные примеры в игре. Linux port и PoE2 support независимы: каждый тестируется отдельной матрицей, а не одним общим «кроссплатформенно».

Лиги получать разрешённым способом из документированного источника/провайдера. Не хардкодить текущую лигу и не выбирать её только по подстрокам названия: использовать category, rules, start/end, realm. Дать выбор Trade/Hardcore/Standard в пределах реально доступных данных; SSF не предлагать для торговли. Нет прав на получение списка — ручной ID с явной проверкой через источник цен, а не обход API.

При смене лиги/realm/профиля: отменить старые запросы, увеличить generationId, очистить текущий рейтинг; поздний ответ предыдущей generation игнорируется. Историю хранить отдельно, не выдавать её за новые цены. Отсутствие лиги в API и окончание сезона — явный статус, не тихая подмена Standard.

## 8. UI: Table / List, сортировки и стиль

Весь UI на английском. Референсы ощущений — Awakened PoE Trade для PoE1 и PoE Overlay 2 для будущего этапа. Это ориентир компактности и взаимодействия, не разрешение копировать брендинг, ресурсы или целиком их функции. Реализация самостоятельная.

Главная панель Opportunities:
- переключатель Table | List, одинаковый набор данных, фильтры, сортировка и выделение. Режим запоминается;
- Table: Route | Net profit | ROI | Gold | Profit/1k gold | Capital | Depth | Data age | Source/quality;
- List: компактные строки-карточки с маршрутом и теми же ключевыми метриками; раскрываемые шаги. Это виртуализированный список, а не тысячи тяжёлых карточек;
- сортировки в обоих режимах: Net profit, ROI, Gold cost, Profit per 1,000 gold, Capital required, Data age; ascending/descending. По умолчанию Net profit descending; быстрые пресеты Most profit, Least gold, Best profit/gold;
- числа сортируются численно, не как текст. При равенстве — стабильный tie-breaker по ID. Сортировка не запускает повторную загрузку;
- фильтры: минимальная прибыль, максимальный капитал/золото, тип маршрута, допустимая задержка; доступные числа и неизвестные значения показаны честно;
- сохранить выделение и scroll anchor при обновлении. Никаких скачущих строк под мышью: при наведении/раскрытии можно временно зафиксировать порядок с индикатором New results available;
- детали: фактическая партия, каждая покупка/продажа, NPC-конверсия, остатки, расходы валюты и золота по шагам, итог, источник/время каждой ноги и допущения;
- шапка: League, Market, Candidates/Observed, Last source observation, Fetched, Next refresh, Refresh now, status. Unknown/Estimated и предупреждение Verify in game не прятать в tooltip; не подсвечивать исторический кандидат как подтверждённый current profit.

Внешний вид: тёмный угольно-коричневый фон, тонкие рамки, приглушённый золотой акцент, светлый читаемый текст, зелёный/красный только по смыслу. Токены в одном ResourceDictionary. Контраст основного текста >= 4.5:1 на используемом фоне; тест и ручная проверка на игровом кадре. Прозрачность настраивается, без realtime blur/Acrylic, бесконечных анимаций и тяжёлых теней. Системный Segoe UI на Windows, системный sans-serif fallback на Linux; не распространять Windows-шрифты. Без скачивания шрифтов и зависимости от CDN. Проверять геометрию на обоих семействах метрик.

По умолчанию небольшая панель сбоку, не поверх центра и нижнего HUD; положение/размер запоминаются на монитор и DPI. Отдельный компактный список топ-N. Не дублировать ненужные окна price-check.

Оверлей — собственное frameless top-level окно: на Windows Topmost/tool window, no-activate для пассивного режима, исключение из taskbar/Alt+Tab. Click-through переключаемый. Редактирование настроек — явный интерактивный режим, допускающий получение фокуса. На Windows Per-monitor DPI v2; в общем UI Avalonia scaling без ручного двойного масштабирования. Корректная смена монитора и отрицательные координаты.
Настраиваемые RegisterHotKey: показать/скрыть, interactive/click-through, refresh. При невозможности регистрации показать конфликт ОС; не обещать автоматически распознать все игровые бинды. Никаких глобальных перехватчиков ввода.

## 9. Архитектура и расход ресурсов

Solution:
- FlipOverlay.Core — чистая доменная библиотека: money/ratios, recipe graph, sizing, ranking, freshness. Без Avalonia, platform interop, HTTP, SQLite.
- FlipOverlay.Infrastructure — providers, HTTP scheduler, storage, settings, release checker. Контракты источников с capabilities и marketKind.
- FlipOverlay.App — Avalonia, MVVM и virtualized views.
- FlipOverlay.Platform.Windows — Win32 только для собственных окон и hotkeys, OS-specific paths/credentials.
- FlipOverlay.Platform.Abstractions — контракты возможностей без Win32/Avalonia-specific handles: IOverlayWindowService, IHotkeyService, IAppPaths, ICredentialStore, IExternalLinkLauncher. Avalonia-specific handles остаются внутри App/platform bridge. Linux-реализацию добавлять отдельным этапом; для CI допустим явный Unsupported/NoOp adapter, не выдаваемый за готовый overlay.
- FlipOverlay.Tests — unit/integration офлайн и контрактные фикстуры.
- tools/Diagnostics — headless selftest/benchmark/проверки сборки; не запускать второй процесс постоянно с GUI.

Работать одним процессом, workstation GC по умолчанию; не форсировать GC.Collect и не менять GC-настройки без профиля. Сеть, SQLite и расчёты вне UI-потока; все очереди ограничены, устаревшие задания отменяются. Не пересоздавать тысячи VM на каждый tick. В видимом окне обновлять Age не чаще раза в секунду, в скрытом UI tick отключить; истечение валидности обслуживает планировщик. Без постоянного render loop.

Ограничить кэш: по умолчанию до 5,000 отображаемых маршрутов, 50 MB памяти под котировки/индексы; историческую БД до 100 MB с пакетной очисткой, логи до 10 MB ротацией, без сырых огромных payload по умолчанию. Размеры настраиваемые. При превышении — предсказуемое отсечение с баннером, не бесконтрольный рост. Инкрементальное получение и сохранённый cursor вместо перекачки истории с начала.

Целевые бюджеты, НЕ неподтверждённые обещания:
- reference PC: Windows 11, x64 CPU от 4 физических ядер, 16 GB RAM; записать точные CPU/ОС/версию сборки. Release, без debugger, локальная воспроизводимая фикстура;
- idle за 10 минут без сетевого/расчётного задания: CPU <= 0.5% всей машины, private bytes <= 150 MB;
- после обновления 10,000 котировок и 5,000 уже подготовленных маршрутов: возврат к idle <= 5 секунд; пик private bytes <= 250 MB; RAM не растёт монотонно за 30 циклов;
- расчёт этих 5,000 маршрутов p95 <= 200 ms, сортировка/переключение Table/List p95 <= 100 ms, без блокировки UI дольше 50 ms. Отдельно измерять первоначальную генерацию маршрутов, а не прятать её вне benchmark;
- UI до состояния «загрузка/нет данных» <= 2 секунд cold start. Время первой сетевой таблицы измерять отдельно и не ставить равным старту UI;
- в скрытом состоянии — без непрерывной GPU-активности приложения и отрисовки. Сравнить игровой benchmark без/с оверлеем: три парных прогона одинаковой сцены, median и p95/p99 frametime. Не объявлять любой разброс доказательством влияния; целевой регресс p95 не больше 2%, указать шум и условия.

Измерить средствами .NET/Windows, сохранить raw measurements в docs/PERFORMANCE.md. При превышении — профилировать конкретный участок и исправлять; не придумывать результаты и не переходить на другой стек без согласования.

### 9.1 Linux: граница переносимости

Avalonia переносит интерфейс, а не гарантирует возможности оверлея у любого оконного менеджера. Общие расчёты/HTTP/SQLite/Table/List должны быть переносимы с первого дня. Window positioning, always-on-top, прозрачность, input passthrough, global shortcuts, tray и credential storage — отдельные capabilities.

Первый будущий Linux gate: одна явно выбранная поддерживаемая Ubuntu LTS x64, PoE через Steam/Proton, сначала X11; Wayland/XWayland — отдельная матрица по compositor и версии, а не обещание «везде работает». Использовать только разрешённые desktop APIs/порталы. Если среда не разрешает нужную функцию — показать Unsupported и обычное companion-window; не выдавать его за равноценный overlay и не обходить ограничения compositor. Не требовать root и не захватывать ввод. Linux end-to-end тесты и упаковка tar.gz/AppImage обсуждаются отдельным этапом, не раздувать первый Windows-релиз.

Требование к spike: составить capability matrix Windows / Linux-X11 / Linux-Wayland: verified, documented-only или unverified; не помечать непроверенное как supported. До реализации PoE2/Linux-порта сохранять ту же политику свежести, безопасности и ограничения ресурсов.

## 10. Установщик и portable

Одна self-contained publish-папка, два артефакта одной версии и коммита:
- PoE-Flip-Overlay-<version>-setup.exe: Inno Setup, per-user в LocalAppData/Programs, без админа, ярлыки, uninstall; данные в отдельном LocalAppData-каталоге приложения. Обновление сохраняет настройки. Удаление данных — отдельная явная опция, выключенная по умолчанию.
- PoE-Flip-Overlay-<version>-portable.zip: распаковать и запустить exe без установки .NET; portable.flag однозначно включает portable. Не определять режим по существованию произвольной папки data.

Portable хранит свои настройки, БД, логи и temp в user-data рядом с exe, не создаёт registry entries/ярлыки/автозапуск и не пишет пользовательские данные в AppData. Не обещать отсутствие системных следов Windows, Defender, crash reporting и т.п. CSV вне папки разрешён только при явном выборе пути пользователем.
Read-only папка: понятная ошибка без скрытого fallback в AppData. Для будущего Linux installed-mode — XDG_CONFIG_HOME/XDG_DATA_HOME/XDG_CACHE_HOME через IAppPaths, portable-mode — те же локальные user-data semantics; не вшивать Windows-пути в Infrastructure. Второй экземпляр не открывает ту же БД на запись; single-instance с контекстом каталога данных. Обновление portable: инструкция сохранить user-data, заменить binaries, не затереть данные шаблоном из ZIP.

Архив: одна верхняя папка, только относительные POSIX entry paths, без traversal, secrets и реальных пользовательских данных. SHA256SUMS для setup/ZIP. Размер измерять, не требовать нереалистичный предел до пробной self-contained сборки. Windows smoke test: распаковать реальный ZIP в путь с пробелами и Unicode, запустить offline selftest, проверить return code и версию. Установку/удаление тестировать на чистой Windows VM. OS-проверки не заменять macOS/Linux-сборкой.

## 11. Проверка GitHub-обновлений

Нужна проверка обновлений самого приложения, не самоустановка.
GET releases/latest для настроенного owner/repo через GitHub API, timeout, User-Agent приложения, ETag и кэш; stable channel. При старте — отложенно и только если с последней проверки прошло 24 часа. Кнопка Check for updates — отдельная команда с защитой от повторов и лимитами. Repo ещё не задан — тихо Disabled.

Версия в Directory.Build.props, используется сборкой, UI и именами артефактов; semver-совместимый разбор, не строковое сравнение. Баннер Update available, ссылка только на проверенный HTTPS GitHub release нужного репозитория; предпочтение setup/portable по режиму. Не скачивать, не выполнять, не заменять файлы автоматически. Ошибка не мешает котировкам. Никакой телеметрии.

Секреты не в git/logs/CSV/fixtures. По умолчанию приложение не требует cookies аккаунта. Если согласованный OAuth нужен, использовать безопасное хранение и документировать привязку защиты к Windows-пользователю; «portable» не значит переносимость защищённого токена между ПК.

## 12. План и проверяемая готовность

Сначала план до пяти пунктов; не заканчивай работу одним планом.
1. Data/policy spike: снять gate доступности свежего источника. Одновременно пробная Avalonia self-contained сборка: виртуализированные Table/List на 5,000 строк, Topmost/click-through/no-activate/hotkeys поверх игры, DPI, idle/visible/hidden measurements. Проверить cold start, прозрачность и render backend на реальном GPU. Linux CI проверяет компиляцию общих модулей; одного headless smoke недостаточно для обещания Linux-оверлея. При data-blocker честно остановиться и запросить решение; offline tests допустимы, выдавать каркас за продукт — нет.
2. Ядро и тесты: рецепты, расчёт партии/профита/золота, качество, валидность, сортировка, смена контекста.
3. Реальные разрешённые провайдеры, планировщик, хранение, отмена и защита от поздних ответов.
4. Avalonia Table/List UI, Windows own-window adapter, стиль, DPI; профилирование и фиксация бюджетов.
5. Setup + portable, Windows smoke tests и живой прогон с PoE1. Публикация — отдельное разрешение.

Обязательные тесты:
- исходная старая котировка, скачанная сейчас, НЕ свежая; повторный snapshot/304 не сбрасывает её возраст;
- часовая история не становится LiveQuote, historical volume не становится depth;
- Unknown source timestamp/gold/depth не превращается в ноль или подтверждённые данные;
- buy/sell направление, невозможность вывести spread из одного среднего, корректные партии/остатки и все сборы;
- расходы золота на обеих exchange-ногах и отсутствие деления на ноль;
- корректное поведение на истечении срока без сети, 429/Retry-After, 401/403, отмена, offline, ручной refresh без параллельных запросов;
- поздний ответ старой лиги не меняет новый рейтинг;
- Table и List имеют идентичные ID/порядок/числовую сортировку; unknown в конце для обоих направлений;
- выбор/скролл не сбрасываются при обновлении; виртуализация реально включена;
- fake game profile без изменения ядра, независимые fee models PoE1/PoE2, рецепты доступны только подходящему патчу;
- общий UI и ядро собираются в Linux CI без загрузки Windows native libraries; capabilities Unsupported обрабатываются явно;
- Candidates не попадают в Observed от нажатия Refresh; агрегатная mean price не становится bid/ask, Wealthy disabled до подтверждения доступа;
- версии new/equal/old/prerelease/malformed и сетевые ошибки update-checker;
- portable paths/read-only/second instance, upgrade сохраняет данные, оба артефакта содержат одну версию.

Команды проверки: dotnet restore --locked-mode; dotnet build -c Release --no-restore; dotnet test -c Release; dotnet format --verify-no-changes. Добавить воспроизводимый tools/build.ps1 для publish/ZIP/Inno Setup и tools/verify.ps1 для Windows-проверок. Selftest разделить на offline (код 0 без сети и аккаунта) и live диагностику с явным статусом источника; не заставлять CI проходить аккаунтную авторизацию.

Критерий «готово»: не только зелёные unit-тесты, а согласованный после data-spike режим продукта, разрешённые реальные данные с честной задержкой, проверенные расчёты, оба представления и сортировки, замеренные ресурсы, работающие setup/portable и ручной прогон поверх PoE1. Приёмка Candidates/manual не закрывает live-data gate; релиз явно документирует, какая часть автоматизирована и что пользователь проверяет сам. Если что-то недоступно, перечислить незакрытые gates, не называть версию production-ready.

Итоговый отчёт: пути артефактов, что реализовано, источники/задержки, реальные выводы проверок, ресурсы/условия измерений, что не проверено и почему. Не подставлять демонстрационные цены в production UI и не выдумывать скриншоты/замеры. Демонстрационные данные — только явно помеченные offline fixtures в тестах и benchmark.

Один согласованный коммит на логически законченный этап. Не пушить, не создавать теги и релизы без отдельного запроса. Не расширять MVP price-check редких вещей, OCR, PoE2, облачным backend или ботом.
